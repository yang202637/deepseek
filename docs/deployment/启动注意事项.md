# 项目启动注意事项说明书

> 适用版本：辰光 Agent 平台（chenguang-agent-platform-v4）
> 最后更新：2026-10-25

本文档说明如何在**本机（Windows 11，无需 Docker）**启动前后端，并记录启动过程中需要特别注意的事项与本次修复内容。

---

## 1. 技术栈与环境要求

| 组件 | 版本 / 要求 | 本机实测 |
|------|------------|---------|
| Python | 3.10 及以上（项目基于 3.13 开发） | 3.13.15（`D:\python\python313`） |
| Node.js | 18 及以上 | v24.22.0 |
| npm | 随 Node 附带 | 11.19.1 |
| 数据库 | 无需 MySQL，使用 SQLite 文件库 `chenguang.db` | 已就绪 |
| 缓存 | 无需 Redis，使用 `fakeredis` 内存实现 | 已就绪 |
| 对象存储 | 无需 MinIO，使用内存模拟 `mock_minio` | 已就绪 |

> 本项目已切换为**免 Docker 本地开发模式**：数据库、缓存、文件存储全部使用本地/内存实现，无需启动 MySQL、Redis、MinIO 容器。

---

## 2. 一键启动（推荐）

直接双击项目根目录的 `start.bat`，脚本会自动完成：

1. 检查 Python 环境
2. 检查/重建虚拟环境 `.venv`（**含损坏检测**，见下文）
3. 安装后端依赖（`pip install -r requirements.txt`）
4. 初始化/升级数据库（`bootstrap_db.py`）
5. 安装前端依赖（`npm install`）
6. 启动后端（8080）与前端（5173）
7. 轮询等待服务就绪，并自动打开浏览器

---

## 3. 手动启动

后端（项目根目录）：

```bat
.venv\Scripts\python.exe -m uvicorn src.main:app --host 127.0.0.1 --port 8080
```

前端（`app` 目录，本机执行策略禁用了 `npm.ps1`，必须用 `npm.cmd`）：

```bat
cd app
npm.cmd run dev
```

## 5. 本次启动修复记录（2026-10-25）

本次在本机启动时发现并修复了以下问题：

1. **虚拟环境损坏**：`.venv` 是另一台机器（`C:\Users\admin\...`）创建的，其 `python.exe` 指向不存在的解释器，导致启动失败。
   - 处理：删除并基于本机 Python（`D:\python\python313\python.exe`）重建 `.venv`，重新安装依赖。
2. **`start.bat` 无法识别损坏的虚拟环境**：原脚本只判断 `.venv\Scripts\python.exe` 文件是否存在，不校验其是否可用。
   - 处理：新增「可用性探测」——对已存在的虚拟环境执行 `python -c "import sys"` 做校验，失败即自动删除并重建。
3. **MinIO 客户端导致后端启动阻塞约 18 秒**：`minio_client.py` 仍引用真实 `minio` 包，启动时向 127.0.0.1:9000 发起连接，因无 MinIO 服务而重试约 18 秒后才失败。
   - 处理：将 `minio_client.py` 接入已存在但未启用的 `mock_minio.py` 内存实现，后端启动时间从约 18 秒降至约 1 秒，且文件上传功能可在内存中正常工作。

## 6. 注意事项（务必阅读）

### 6.1 `start.bat` 的编码与换行
`start.bat` **必须保存为 GBK 编码 + CRLF 换行**，原因：

- 脚本开头 `chcp 936` 将控制台切到 GBK 代码页；若文件为 UTF-8，中文提示会乱码。
- CMD 在 `chcp 65001`（UTF-8）下读取 UTF-8 批处理会出现文件指针错乱，纯 LF 换行会拆断 `if`/`for` 等复合语句。

> 如需用编辑器修改 `start.bat`，修改后请确认仍为 **GBK + CRLF**，否则脚本可能异常。

### 6.2 虚拟环境
- 虚拟环境位于 `.venv`，由本机系统 Python 创建。
- 若换了机器/移动了项目/升级了 Python，旧 `.venv` 可能失效；此时直接运行 `start.bat`，脚本会自动检测并重建（本次新增的修复）。
- 若需手动重建：`rmdir /s /q .venv` 后重新运行 `start.bat`，或 `python -m venv .venv && .venv\Scripts\python.exe -m pip install -r requirements.txt`。

### 6.3 数据库
- 使用 SQLite 文件 `chenguang.db`，**无需 MySQL**。
- `bootstrap_db.py` 会自动处理：首次建库灌数据、缺迁移版本表时打标、迁移升级、迁移失败时备份旧库（`chenguang.db.bak_<时间戳>`）后重建。
- 数据库迁移仍使用 alembic：`.venv\Scripts\python.exe -m alembic upgrade head`。

### 6.4 缓存与文件存储为内存实现
- 缓存：`fakeredis`（内存），文件存储：`mock_minio`（内存）。
- **两者数据在进程重启后即丢失**，仅适用于本地开发与演示，生产环境需替换为真实 Redis / MinIO。

### 6.5 端口占用
- 后端默认 `8080`，前端默认 `5173`。
- `start.bat` 会检测端口占用：已被占用时跳过对应服务的启动（可能已在运行）。
- 停止服务：直接关闭对应命令行窗口。

### 6.6 前端环境变量
- 前端配置在 `app/.env.local`：
  - `VITE_USE_MOCK=false`：走真实后端接口（非 mock 数据）。
  - `VITE_API_BASE=http://localhost:8080/api/v1`：后端 API 地址。
- 若后端端口变更，需同步修改 `VITE_API_BASE`。

### 6.7 依赖清单
- `requirements.txt` 已统一为 **UTF-8** 编码（历史版本曾为 UTF-16，属非标准编码，易导致工具解析异常）。
- 后端依赖已与「免 Docker」模式对齐：不再依赖 `minio` 包（改用 `mock_minio`）。

## 7. 常见问题排查

| 现象 | 原因 / 处理 |
|------|------------|
| `start.bat` 提示「虚拟环境已损坏，正在重建」 | 旧 `.venv` 失效（换机器/换 Python），脚本已自动处理 |
| 后端启动后卡住约 18 秒 | 已修复（接入内存 MinIO）；若复现，检查是否仍引用了真实 `minio` 客户端 |
| 前端能打开但接口 404 | 检查后端是否在 8080 运行，`app/.env.local` 的 `VITE_API_BASE` 是否正确 |
| 登录提示验证码错误 | 登录需填写图形验证码；默认账号 `admin` / `123456` |
| 数据库报错 | 查看 `bootstrap_db.py` 输出；必要时备份 `chenguang.db` 后删除，重新运行启动脚本 |
| `npm` 相关报错 | 确认 Node.js ≥ 18；本机需使用 `npm.cmd`（`npm.ps1` 被执行策略禁用） |
